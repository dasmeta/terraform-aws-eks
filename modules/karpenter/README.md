 # terraform module allows to create/deploy karpenter operator to have custom/configurable node auto-scaling ability
## for more info check https://karpenter.sh and https://artifacthub.io/packages/helm/karpenter/karpenter

## example
```terraform
module "karpenter" {
  source  = "dasmeta/eks/aws//modules/karpenter"
  version = "2.19.0"

  cluster_name      = "test-cluster-with-karpenter"
  cluster_endpoint  = "<endpoint-to-eks-cluster>"
  oidc_provider_arn = "<eks-oidc-provider-arn>"
  subnet_ids        = ["<subnet-1>", "<subnet-2>", "<subnet-3>"]

  resource_configs = {
      nodePools = {
        general = { weight = 1 } # by default it use linux amd64 cpu<6, memory<10000Mi, >2 generation and  ["spot", "on-demand"] type nodes so that it tries to get spot at first and if no then on-demand
        on-demand = {
          # weight = 0 # by default the weight is 0 and this is lowest priority, we can schedule pod in this not
          template = {
            spec = {
              requirements = [
                {
                  key      = "karpenter.sh/capacity-type"
                  operator = "In"
                  values   = ["on-demand"]
                }
              ]
            }
          }
        }
      }
    }
}
```

| <a name="input_termination_grace_period"></a> [termination\_grace\_period](#input\_termination\_grace\_period) | Upper bound on how long a node may take to drain before karpenter removes the remaining pods and<br/>terminates it. Unset by default, and that default is deliberate.<br/><br/>READ THIS BEFORE SETTING IT. Configuring a terminationGracePeriod does not merely bound a drain that has<br/>already started -- it changes what karpenter is willing to disrupt in the first place. Karpenter's<br/>documentation is explicit: nodes with active `karpenter.sh/do-not-disrupt` pods are "conditionally<br/>excluded from Drift", and "if the Node's owning NodeClaim has a terminationGracePeriod configured, it<br/>will still be eligible for disruption via drift". Once the period elapses, pods are force-deleted, and<br/>that "includes pods with blocking pod disruption budgets or the karpenter.sh/do-not-disrupt annotation".<br/><br/>So setting this converts both protections from absolute into a delay:<br/><br/>  unset  -> a node hosting a do-not-disrupt pod or a blocking PDB is NEVER drifted. It keeps its old AMI<br/>            until a human moves the workload.<br/>  set    -> that node IS drifted, and the protected pods are force-deleted when the period expires.<br/><br/>Leaving it unset is the safer position: a workload marked always-up stays up, and the node simply keeps<br/>an older AMI until someone handles it deliberately -- often with a prepared flow that cools the workload<br/>down, replaces the node and brings it back. Losing that workload to an unattended AMI roll is worse than<br/>running an older AMI for a few days.<br/><br/>The cost is that a node with a genuinely broken budget can stay Deleting indefinitely. Fix the budget<br/>rather than setting this: the base chart refuses to render a zero-eviction PDB, and section E1 of<br/>`scripts/eks-assess.sh` lists any that already exist.<br/><br/>Set it only on a cluster with a known stuck-node problem you cannot fix at source, and understand that you<br/>are trading away the guarantee that do-not-disrupt and PDBs are honoured. | `string` | `null` | no |
